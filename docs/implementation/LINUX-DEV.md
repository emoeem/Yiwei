# Linux 桌面端开发：窗口打开但没有界面

症状：`cargo run` 后窗口出现了，但里面什么都没有（空白），控制台可能伴随
`Failed to create GBM buffer of size <W>x<H>: 无效的参数` 反复出现。

这不是同一个问题，是**两个互相独立**的原因叠在一起，先分清再修。

## 原因零（本机实际原因）：Linux 上 `pnpm tauri dev` 走 CEF，而 CEF 归档没下完

`scripts/tauri.mjs` 在 Linux 上把 `dev` / `build` / `bundle` 切到 **CEF（Chromium）运行时**
（`--features cef` + `--no-default-features` + `src-tauri/.cargo/cef.toml`），
非 Linux 平台才是 wry/系统 WebView。CEF 发行包首次构建时下载到
`~/.cache/tauri-cef/<cef-version>/`。

本机实测：这次下载**只完成了 50 MB / 306 MB** 就被中断，报错是：

```
CEF_PATH does not exist, downloading archive to: /home/emo/.cache/tauri-cef/151.3.24
Error: File I/O error: Peer disconnected
```

更麻烦的是它会留下**半成品解压目录**，下一次构建看到目录已存在就跳过解压，于是报出
误导性的 rename 错误：

```
failed to rename file from .../cef_binary_..._minimal/CMakeLists.txt
  to .../cef_linux_x86_64/CMakeLists.txt: No such file or directory
```

修复步骤（保留已下载的归档，不重复下载 306 MB）：

```bash
CACHE=~/.cache/tauri-cef/151.3.24
# 1. 把残留的解压目录挪开（不要删归档）
mv "$CACHE"/cef_binary_*_minimal "$CACHE"/cef_binary_*_minimal.stale
mv "$CACHE"/cef_linux_x86_64       "$CACHE"/cef_linux_x86_64.stale
# 2. 确认归档完整（完整包约 306 MB，bzip2 不应报 "ends unexpectedly"）
ls -l "$CACHE"/*.tar.bz2
tar -tjf "$CACHE"/*.tar.bz2 > /dev/null && echo OK
# 3. 重新构建
pnpm tauri dev
```

归档不完整时，直接重下正确的那个（版本号与文件名以报错信息为准）：

```bash
curl -L --retry 3 -o /tmp/cef.tar.bz2 \
  "https://cef-builds.spotifycdn.com/cef_binary_151.3.24+g2384915+chromium-151.0.7922.174_linux64_minimal.tar.bz2"
tar -tjf /tmp/cef.tar.bz2 > /dev/null && mv /tmp/cef.tar.bz2 "$CACHE"/
```

首次 CEF 构建要编译约 1200 个 crate，比 wry 路径慢得多，请耐心等。

## 原因零点五：`cargo run` 报 "failed to read plugin permissions"

```
error: failed to run custom build command for `Readest v0.2.2 (...)`
  thread 'main' panicked at src-tauri/build.rs:72:6:
  failed to run tauri-build: failed to read plugin permissions
  Caused by: failed to read file
    '~/.cargo/registry/src/<registry>/tauri-plugin-oauth-2.1.0/permissions/autogenerated/commands/cancel.toml':
    No such file or directory (os error 2)
```

这不是你的代码问题，是**共享的 cargo registry 缓存被弄坏了**：`permissions/autogenerated/commands/*.toml`
是 tauri 插件的 build script 生成到 crate 源码目录里的，而 CEF 构建用的是另一套 tauri 版本
（`feat/cef` 分支），它会重新生成/清掉这些目录。wry 那条依赖图随后读到的是被清空的目录，
但 `.cargo-ok` 还在，cargo 认为"已解压"因而不会重来一遍。

2026-09-16 本机实际受影响的 5 个 crate：

```
tauri-plugin-device-info-1.0.1   tauri-plugin-oauth-2.1.0    tauri-plugin-sentry-0.5.0
tauri-plugin-sharekit-0.3.1      tauri-plugin-sign-in-with-apple-1.0.2
```

**先用这个方法确认是不是这一类问题**（比对解压目录与 `.crate` 原始包的文件数）：

```bash
reg=$(basename "$(ls -d ~/.cargo/registry/cache/*/)" )
cd ~/.cargo/registry
for crate in cache/$reg/*.crate; do
  name=$(basename "$crate" .crate)
  src=src/$reg/$name
  [ -d "$src" ] || continue
  exp=$(tar -tzf "$crate" 2>/dev/null | grep -vc '/$')
  act=$(( $(find "$src" -type f | wc -l) - 1 ))   # 减掉 .cargo-ok
  [ "$exp" = "$act" ] || echo "损坏: $name 期望=$exp 实际=$act"
done
```

**修复**：把损坏目录挪开，用缓存里的 `.crate` 重新解压并补回 `.cargo-ok`
（原始包是完整的，不需要联网）：

```bash
reg=<registry 名，例如 rsproxy.cn-xxxxxxxx>
cd ~/.cargo/registry/src/$reg
for name in tauri-plugin-oauth-2.1.0; do
  mv "$name" "$name.broken-$(date +%Y%m%d)"
  tar -xzf ~/.cargo/registry/cache/$reg/$name.crate
  printf '{"v":1}' > "$name/.cargo-ok"
done
cd /path/to/readest/apps/readest-app/src-tauri && cargo build
```

要避免它再发生，就不要在同一个 checkout 里交替跑 `pnpm tauri dev`（CEF）和
`cargo run`（wry）——选一条路径用到底，或者交替前先按上面的方法检查一遍。

## 原因一：`cargo run` 需要有一个正在运行的 dev server

debug 构建（没有 `custom-protocol` feature）用的是 `tauri.conf.json` 的
`build.devUrl`，也就是 `http://localhost:3000`，**不是** `build.frontendDist`（`../out`）。
所以：

- `pnpm tauri dev` —— 官方入口，会同时起 Next dev server 和桌面壳。
- `pnpm dev-web` + `cargo run` —— 也可以，但两个进程必须都在。
- 只跑 `cargo run`、而 3000 端口没有服务 —— WebKit 拿到的是一个加载失败的页面，
  看起来就是"窗口打开了但没有任何元素"。

要做**独立运行**（不需要 dev server）必须先构建前端，再用 release 构建：

```bash
pnpm --filter @readest/readest-app build   # 生成 out/，会被编译进二进制
cd apps/readest-app/src-tauri && cargo run --release
```

### 怎么确认是哪一种

看 dev server 的日志：

- 只有 `GET /` 和 `GET /runtime-config.js`，**没有任何 `/_next/static/chunks/*`** ——
  webview 拿到了 HTML 但从未执行 JS，属于加载/渲染问题。
- 有几十条 `/_next/static/chunks/*` —— 前端正常加载，问题在别处（例如主题/CSS）。

## 原因二：WebKitGTK 在 Wayland 下的合成失败（GBM buffer）

Wayland（niri / GNOME / KDE 原生会话）+ 混合显卡或 NVIDIA 私有驱动时，WebKitGTK 的
DMA-BUF 渲染路径会分配缓冲区失败，典型报错：

```
Failed to create GBM buffer of size 948x1014: 无效的参数
```

上游自己的规避办法写在 `flake.nix` 的 dev shell 里：`GDK_BACKEND = "x11"`。

本机（niri + RTX 4050 / Radeon 680M 混合）实测：

| 启动方式 | GBM 报错 | 界面是否渲染 |
| --- | --- | --- |
| 默认（Wayland） | 0 | ✅ 渲染正常 |
| `WEBKIT_DISABLE_DMABUF_RENDERER=1` | 0 | ✅ 渲染正常 |
| `GDK_BACKEND=x11` | 4 | ✅ 渲染正常 |

结论：**GBM 报错本身不等于白屏**（上表第三行报了 4 次错但界面照样出来了），
但它是渲染路径不健康的信号，遇到白屏时应当先排除它：

```bash
WEBKIT_DISABLE_DMABUF_RENDERER=1 pnpm tauri dev
# 或者
GDK_BACKEND=x11 pnpm tauri dev
```

## 排查用的验证方法

无法肉眼看截图时（例如在自动化环境里），可以用「截图 + 差异 + OCR」判断界面到底画了什么：

```bash
niri msg action focus-workspace <空工作区>      # 排除其他窗口干扰
grim /tmp/shot_empty.png                        # 空桌面
pnpm tauri dev &                                # 起应用
grim /tmp/shot_app.png                          # 带应用的桌面
# 两张图求差异得到窗口区域，再看窗口内的颜色分布与文字
tesseract /tmp/app_window.png stdout -l chi_sim
```

窗口内出现书名（例如书架的 demo 书籍）就说明前端确实渲染了；只有一个纯色说明是白屏。

## 任务栏/状态栏（Waybar 等）不显示图标

Waybar 的 `wlr/taskbar` 模块**不读窗口的 `_NET_WM_ICON`**，它是拿窗口的 `app_id`
去 GTK 图标主题里查同名图标（等价于 `Gtk.IconTheme.lookup(app_id)`）。所以链路有两个环节，
缺一个就是空白：

1. **`app_id` 必须有名字且可预测。** GTK 在 Wayland 下用二进制名当 app_id，dev 构建原来的
   二进制叫 `Readest`，于是 app_id 是 `Readest`。
   已在 `src-tauri/Cargo.toml` 里显式声明 `[[bin]] name = "yiwei"`，与
   `tauri.conf.json` 的 `mainBinaryName` 对齐（同时窗口标题由 Rust 端显式设为 `Yiwei`，
   窗口图标也改为显式使用 `bundle.icon` 里嵌入的那份，不再依赖 app_id 回退）。
   验证：`niri msg --json windows` 里应看到 `title='Yiwei' app_id='yiwei'`。
2. **图标主题里得有同名图标。** 开发时没有安装步骤，所以需要手动放一份到用户主题目录
   （`hicolor` 在 GTK 的默认搜索路径内）：

```bash
python3 - <<'PY'
from PIL import Image
import os
src = Image.open('data/icons/yiwei/icon.png').convert('RGB')
base = os.path.expanduser('~/.local/share/icons/hicolor')
for s in (16, 24, 32, 48, 64, 128, 256, 512):
    d = f'{base}/{s}x{s}/apps'
    os.makedirs(d, exist_ok=True)
    src.resize((s, s), Image.LANCZOS).save(f'{d}/yiwei.png')
PY
```

验证图标能被解析到（这一步通过就等于 Waybar 能查到）：

```bash
python3 -c "import gi; gi.require_version('Gtk','3.0'); from gi.repository import Gtk; \
print(Gtk.IconTheme.get_default().lookup_icon('yiwei', 128, 0).get_filename())"
```

Waybar 可能缓存了图标，改完重启一次：`pkill waybar`（若有 systemd 服务会自动拉起）。

**打包发行版时还要复核一次**：确认安装到 `/usr/share/icons/hicolor/*/apps/` 的图标文件名
与 app_id 一致（Tauri 打包器按 `bundle.icon` 安装，命名规则在预编译的 CLI 里，本地无法查）。
如果名字大小写或前缀不一致，Waybar 仍会显示空白。

## 已知的开发期遗留

Rust **crate 名**仍是 `Readest`（包名，不是二进制名）：`cargo -p Readest` 的脚本、
Sentry release 名（`sentry_config.rs` 用 `CARGO_PKG_NAME`，需与
`scripts/upload-sourcemaps.mjs` 的 `Readest@<version>` 保持一致）都依赖它。改包名会重写
`Cargo.lock` 与 `Cargo.cef.lock`，需要专门做一次。
